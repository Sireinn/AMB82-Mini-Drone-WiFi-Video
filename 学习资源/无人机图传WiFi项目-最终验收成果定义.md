# 一、项目定位与最终目标

项目核心定位

# 基于 AMB 82-Mini 的无人机 Wi-Fi 图传模块开发

基于指定的 AMB 82-Mini 开发平台，实现实时视频无线传输，以及与无人机飞控之间的双向通信和协议指令下发。

最终目标： 完成一套可以在桌面环境独立运行的无人机 Wi-Fi 图传原型系统，具备视频采集、无线传输、地面端显示和飞控协议命令发送能力，并完成系统性能测试与优化。

这里要特别明确：

项目的最终交付是完整的桌面图传系统，不要求将模块实际安装到无人机上，也不要求实际飞行测试。

但是，飞控通信功能不能省略。

1. 视频无线传输系统。
    
2. 飞控双向通信系统。

## 三、必须实现的三条数据链路

这是整个项目最核心的技术要求。

|链路|数据方向|具体功能|
|---|---|---|
|视频下行|AMB 82 → 电脑|摄像头画面实时传输|
|飞控数据上行|飞控 → AMB 82 → 电脑|飞控数据返回地面端|
|控制命令下行|电脑 → AMB 82 → 飞控|按飞控协议发送命令|

其中第三条是老师特别补充的要求，不能遗漏。

反向控制的具体含义：

地面电脑生成符合飞控通信协议的命令，经 Wi-Fi 发送到 AMB 82-Mini，再由 AMB 82 通过 TTL UART 接口输出对应协议报文。

需要注意，飞控遥测数据显示目前还没有明确列为硬性要求，但建议实现基本的通信状态和命令应答监测。

# 四、项目验收标准

我建议把验收分为四大类，共十二项。

## A. 视频图传功能

核心必做

|编号|验收项目|验收标准|
|---|---|---|
|A 1|摄像头采集|AMB 82 能正常获取摄像头图像|
|A 2|视频编码|能够生成可解码的视频流|
|A 3|Wi-Fi 传输|能够通过无线网络传输视频|
|A 4|地面端显示|Windows 电脑能够实时接收和显示画面|
|A 5|视频录像|能够保存接收到的视频（建议纳入）|

建议第一版直接采用官方 RTSP 示例，利用 VLC 完成基础接收。

后续再根据开发进度决定是否开发独立地面端软件。

## B. 飞控通信与命令下发

核心必做

|编号|验收项目|验收标准|
|---|---|---|
|B 1|UART 通信|AMB 82 与飞控串口能够连接|
|B 2|协议适配|能够按照实际飞控支持的协议处理数据|
|B 3|命令生成|能够生成符合协议要求的命令报文|
|B 4|命令下发|命令能够通过 AMB 82 的 TTL 接口输出|
|B 5|飞控识别|尽可能通过实际飞控验证命令接收及应答|

这里特别说明：

- MAVLink 是候选协议，不是已经确定的协议。
    
- 需要先确认实验室飞控型号、固件和串口配置。
    
- 不需要自主开发飞控固件。
    
- 不需要自主开发飞行控制算法。
    
- 不要求通过这套系统实际操纵无人机飞行。
    

初期可以使用查询状态、请求参数等非运动类命令验证协议链路。

## C. 系统集成

核心必做

|编号|验收项目|验收标准|
|---|---|---|
|C 1|视频与通信并行|视频传输和 UART 通信同时运行|
|C 2|连续运行|系统能够持续工作，无异常重启|
|C 3|异常处理|能够识别网络断开、串口异常等情况|

这一部分非常重要。

我们不能只证明视频单独运行没问题、串口单独运行没问题。

最终要证明两条链路能够同时运行。

## D. 性能测试与优化

核心测试与改进

|指标|测试内容|
|---|---|
|分辨率|支持的视频分辨率|
|帧率|实际稳定 FPS|
|延迟|视频端到端延迟|
|距离|不同距离下的视频传输表现|
|丢包|数据丢失、卡顿情况|
|稳定性|长时间运行情况|
|功耗|开发板实际工作功耗|
|重量|整套机载模块重量|

这些指标建议先测试基线，再逐步优化。

## 图传性能目标

# 720 P

初期目标分辨率

# ≥15 FPS

初期目标帧率

# ≤300 ms

初期延迟优化目标

# 30 分钟

无线测试

- 近距离基础测试。
    
- 10 米地面视距测试。

- 命令传输延迟。

- 连续通信异常次数。

# 八、目前还存在的几个技术待确认项

为了避免后续方案出现偏差，我把目前尚未确定的内容列出来。

|问题|当前状态|影响|
|---|---|---|
|飞控品牌和型号|待确认|决定通信协议|
|飞控使用的固件|待确认|决定协议实现|
|UART 接口电平|待确认|决定硬件连接|
|摄像头具体型号|待采购确认|决定硬件兼容性|
|Wi-Fi 网络模式|待设计|决定通信架构|
|命令下发协议|待飞控资料确认|决定软件实现|
|遥测数据显示|待确认|决定地面端功能|
|性能指标|尚无老师规定|需要制定内部目标|

这里还有一个值得注意的技术设计：视频流建议走 RTSP，控制命令则单独设计网络数据通道，不建议把控制命令混进视频流。这样可以独立处理命令可靠性、超时、应答和权限。

# 九、最终验收流程应该是什么样？

我建议最终演示按照下面的顺序进行：

## 最终项目演示流程

1. 启动机载端
    
    给 AMB 82-Mini 上电，摄像头启动，建立 Wi-Fi 连接。
    
2. 地面端接收视频
    
    电脑连接无线网络，打开接收程序，实时显示摄像头画面。
    
3. 连接飞控
    
    AMB 82 通过 TTL 串口与实验室飞控连接。
    
4. 验证飞控通信
    
    地面端发送协议命令，AMB 82 通过 UART 输出，飞控接收并识别。
    
5. 验证并行工作
    
    保持视频传输的同时，持续进行飞控通信。
    
6. 进行性能测试
    
    测量帧率、延迟、距离、稳定性、功耗和通信成功率。
    
7. 展示最终成果
    
    演示完整系统，提交源代码、硬件资料和测试报告。
    

# 十、我对这个项目的最终判断

现在项目的核心已经很清楚了。

它不是简单地把官方 AMB 82 摄像头示例烧录出来，也不是要我们从零研发一套无人机通信系统。

真正有价值的工作是：

1. 利用官方已有的视频处理能力，搭建稳定的 Wi-Fi 图传链路。
    
2. 实现 Wi-Fi 与 TTL UART 之间的飞控协议数据转发。
    
3. 实现地面端命令通过 AMB 82 到达飞控接口。
    
4. 让视频传输和飞控通信同时工作。
    
5. 通过实验对系统性能进行测量和优化。
    

我认为这五项就是你们项目真正的技术主线。

接下来制定五人分工时，也应该围绕这五项展开，而不是围绕 H.264、UART、Wi-Fi 这些技术名词机械分配。

尤其是要记住：官方已经提供的功能，我们要先复用；真正需要自主开发和验证的功能，才是团队应该投入主要精力的地方。
